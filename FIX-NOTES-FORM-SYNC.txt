  KIT REVISION 6 — DEPLOYMENT HARDENING (cycle 3)
════════════════════════════════════════════════════════════════════

PROBLEM
  The kit deployed fine on a LAN, but going live on a real
  domain left five operational gaps:
  1) .env shipped with ALLOWED_HOSTS=* and CORS_ALLOW_ALL=1
     (any host header accepted, any origin could read API
     responses) and no guided way to tighten them.
  2) No HTTPS path: the nginx template was HTTP-only.
  3) Backups were a one-line tip ("copy those two folders")
     — no command, no schedule, no rotation.
  4) Email setup was two sentences; Resend needs DNS records
     and the right .env keys or nothing sends.
  5) sp.sh restart was broken when invoked as documented
     ("bash sp.sh restart"): it re-called itself via $0, which
     is not on PATH — a latent bug since the first release.

WHAT CHANGED (files touched)
  install.sh
      * New options: --domain=NAME (locks ALLOWED_HOSTS +
        CORS + CSRF origins to the domain incl. www., with
        localhost/127.0.0.1 kept for health checks and local
        admin access), --with-tls (Let's Encrypt via certbot
        webroot; installs the TLS nginx front, flips secure
        cookies + SECURE_SSL_REDIRECT on after certs actually
        issue, rewrites the site's API_BASE to https), and
        --tls-email for the certificate registration.
      * Domain hardening applies to FRESH installs (dedicated
        .env branch) AND to re-runs on existing installs
        (upsert helper rewrites/appends keys; upgrade-safe).
      * TLS flow: HTTP nginx front first (also the ACME
        fallback), certbot certonly (apex+www, retries
        apex-only), then nginx-tls.conf; on any failure it
        reverts to the HTTP front and prints fix-forward
        steps instead of leaving a broken server.
      * systemd installs now also install sp-backup.service +
        sp-backup.timer (daily 02:30, Persistent=true).
      * Banner: public-URL line reflecting TLS state, backup
        line, and a hardening hint on wildcard installs.
  templates/sp.sh
      * New "backup" command: online-safe sqlite snapshot
        (sqlite3 backup API — safe while gunicorn runs),
        bundled with media/ + .env into
        backups/sp-backup-<ts>.tar.gz (archive paths relative
        to backend/ so restore = one tar -x), keeps newest 14.
      * Fixed restart bug ($0 -> $APP/sp.sh absolute path).
  templates/nginx-tls.conf (new)
      * :80 ACME + 301-to-HTTPS; :443 with Let's Encrypt cert
        paths, Mozilla intermediate TLS profile, HSTS (set at
        nginx so it covers the static site too), 12m upload
        limit, same proxy map as the HTTP front.
  templates/sp-backup.service + sp-backup.timer (new)
      * oneshot unit + daily timer for automated backups.
  backend/sporting_pearls_backend/settings.py
      * SECURE_SSL_REDIRECT (env-driven, default 0 — existing
        plain-HTTP installs unaffected).
  EMAIL-SETUP-GUIDE.txt (new, also copied into the app dir)
      * Resend step-by-step: account, domain verification,
        DNS records, API key, .env keys, QC redirect mode,
        troubleshooting table.
  templates/POST-INSTALL-README.txt, README-START-HERE.txt
      * "Going live" hardening section, backup/restore
        commands, new installer options, email guide pointer.

REAL DEFECT FOUND AND FIXED (T65) — throttles were inert
---------------------------------------------------------------------
Symptom: after 8 failed staff logins, the 9th attempt returned 200
(no 429) on the fresh install — yet the same code passed every
Phase 2 test.

Root cause: the shipped service templates ran gunicorn with
--workers 3. The login/reset throttles count in the process-local
cache (R28), so the 8 failures round-robined across three worker
processes and no single counter ever reached the threshold. The
throttle was REAL CODE that was INERT in the default install —
exactly the class of bug only a fresh-install acceptance test can
catch (the Phase 2 tests ran against a single-process runserver).

Fix: templates/sp.sh and templates/sp-backend.service now ship
  --workers 1 --threads 8
One gunicorn process with 8 gthread threads: the throttle counters
are process-shared (and thread-safe through Django's cache API),
SQLite writes stay single-process (no cross-worker "database is
locked"), and concurrency for a small academy comes from threads.
Both templates carry a comment explaining the scaling path:
PostgreSQL + SP_CACHE=db (shared counters) BEFORE raising the
worker count.

Verified on the installed instance: 9th failed staff login → 429
with the branded page; admin surface likewise. The acceptance
script now carries a regression guard (gunicorn must be exactly
master + 1 process) so a future "just raise the workers" change
fails the acceptance run loudly instead of silently disarming the
throttles again.

Remaining owner-side before go-live (unchanged except Phase 6
item now annotated): academy-staff staging sign-off with the same
fictional data (re-run scripts/p6_acceptance.sh at staging), real
production credentials, domain/hosts locking, uptime monitor at
/healthz/ + named operational owner, DSO appointment + DSO_EMAIL.
